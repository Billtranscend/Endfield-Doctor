# 产品需求（用户 2026-11-04 提出）

## 用户原话要点

1. UI 风格类似 OEA：功能列表在左，详细操作在右；平面设计趋向《明日方舟：终末地》的设计语言。
2. 不能让用户等太久。
3. 用户预选蓝图（如 1.6 皇帝产线），程序据此知道哪里堵塞是问题、哪里堵塞或休眠属于正常。
4. 通过简报和基建综合诊断，发现用户**缺少开矿**（未达到该蓝图设计的矿物用量上限）或**缺气液**（野外的惰气、水、息壤气、沉积酸），要告诉用户**哪个区域**缺了什么，让用户自己去补。

## 对设计的影响

### 蓝图档案（data/blueprints/<蓝图名>/）

每套蓝图一个目录，用户在 UI 里预选：

| 文件 | 内容 | 来源 |
|---|---|---|
| `tier_rules.json` | 备路规则、设计限速 | 蓝图预览 + 俯瞰点准入口（见《新蓝图适配》） |
| `reference_brief.json` | 一份**完全按蓝图搭好**的基地的简报（每地区每物品的理论产耗） | 用 `brief_reader.py` 在标准基地上读一次 |
| `sources.json`（可由 reference_brief 生成） | 各地区矿、水、气的设计用量上限 | reference_brief 里没有配方来源的物品的理论生产 |

1.6 皇帝产线的参考简报来自用户 2026-11-04 的第二个账号（完全按蓝图布置）。

### 缺矿 / 缺气液的判断

对每个地区、每种「源头物品」（矿、清水、惰气、息壤气、沉积酸等，配方表里没有生产配方的）：

- 用户简报的**理论生产** = 用户已放置的矿机/泵/气口的满速能力。低于参考值 → 「缺开矿 / 缺水口 / 缺气口」：少放了设备，报「X 地区 Y 理论 a/分，蓝图设计 b/分，缺 (b−a)」。
- 理论够、**当前生产**明显低于理论 → 来源本身供不上（矿点枯竭、气点产量低、泵没接好），报「X 地区 Y 当前 a/分，设计 b/分」。
- 两者都够，但下游缺料 → 走现有的「送不到 / 限速」判断。

以上都只用简报就能判，不用进俯瞰，满足「不让用户久等」。

### 哪些堵塞是正常的

由蓝图档案里的 tier_rules 决定（已实现于 `src/diagnose.py`、`src/combine.py`）：产物爆仓、下游回堵、备路未触发、设计限速 → 正常；其余才报问题或待确认。

### 速度

- 简报读取：每地区约 30–60 秒（翻页 + OCR），两地区约 2 分钟；可以只读用户选的地区。
- 诊断：毫秒级。
- 俯瞰巡检：每屏 10–30 秒，整基地几分钟；作为「深入检查」按钮，不在默认流程里。
- OCR 模型加载一次常驻。

### UI

- 左栏功能：连接游戏 / 选择蓝图 / 简报诊断 / 基建巡检 / 报告 / 设置。
- 右侧详情：当前步骤的操作、进度、结果（问题 / 待确认 / 正常 分组，可展开推断链）。
- 视觉：终末地风格（深色底、黄色强调、工业线条、等宽数字），具体做 UI 时再定稿。
- 技术选型待定：Tauri + Web（和 OEA/MXU 一致，打包小）或 PySide6（和现有 Python 代码同进程）。

## 2026-11-04 补充：报告里的设备定位

用户看不懂「种植机 (763, 837)」这种坐标（原话：「你给我坐标我也不知道在哪啊」）。每条涉及具体设备的结论都要带**截图定位**：扫描时每屏截图留档，报告里给出该设备所在屏的裁剪图、红圈标出设备，并用邻居描述位置（「武陵城西侧，上面挨着装备原件机，右边是取货口那一列」）。坐标只作为程序内部标识，不对用户展示。
