# 终末地基建诊断软件 · 调研报告（视觉能力 + 推算思路）

日期：2026-11-04　状态：调研，未写代码

## 0. 结论先行

1. **技术上可行，而且有现成底座。** MaaEnd 的底座是 MaaFramework（LGPL-3.0）。它已经把我们要的几样东西做好了：窗口截图、鼠标键盘输入、模板匹配、颜色匹配、PaddleOCR、ONNX 模型推理。我们不用从零写视觉，只写「看哪里、怎么理解」。
2. **最有价值、最容易做的第一步是「简报读取器」。** 简报一屏就有每种物品的库存、实际生产/消耗、理论生产/消耗。按分级生产规则一步步推，就能判断大部分问题（昨天用你的简报推过一遍，11 步全对上）。
3. **定位根因要第二步「俯瞰巡检」。** 例如「赤铜块产量低」要定位到「缺水 → 水驱矿机慢 → 赤铜矿不够 → 精炼炉跑不满」，就得点开具体设备，读状态（缺料、阻塞、供给不足）和准入口限速。
4. **准入口需要多少流体，可以算出来，不用看。** 只要知道准入口下游接了哪些设备、各跑什么配方、实际开工率，就能用配方表算出需求，再和限速、管道上限 120/分比较（第 6 节）。
5. **QQ 机器人的两个老问题都能解决：**
   - 看不到全局：程序自己翻遍简报的每个地区，必要时进俯瞰。
   - 识别出错：分辨率固定在 1280×720，OCR 结果只在已知物品名里挑，同名瓶子靠图标里的液体颜色区分。

| 方式 | 速度 | 兼容性 | 后台可用 | 说明 |

| PrintWindow | 中 | 中 | 是 | |
| GDI / DXGI | 快 | 低–中 | 否 | |

**输入方式：**

| 方式 | 兼容性 | 后台可用 | 说明 |
|---|---|---|---|
| Seize | 高 | 否 | 会占用鼠标，也就是 MaaEnd 的做法 |
| SendMessage / PostMessage 系列 | 中 | 是 | Unity 游戏常常不认，需要实测 |

**建议：**
- 默认用 ScreenDC + Seize，和 MaaEnd 一致，已经证明能用。
- 程序**必须以管理员身份运行**。这一点我们前天实际碰到过：自动化进程不是管理员时，输入被系统拦下（UIPI）。
- 诊断时程序会占用鼠标，界面上要提示用户「巡检期间别动鼠标」，并给一个停止热键。
- CapsLock（俯瞰）在 Windows 原生输入里能正常发送，不受我之前工具的限制。

这些踩坑经验都来自前两天手动巡检，做程序时直接写成规则：
- 图标会认错，必须靠悬停或面板的文字名确认（研磨机和塑形机、赤铜瓶和耐压罐都认错过）。
- 息壤和重息壤图标很像，只能靠文字区分。
- 用户改造过的基地（暗管直供、删掉起步口等）在功能上等同于蓝图，按等效实现处理，不报差异。

## 5. 诊断引擎：从读到的数字到结论

数据分三层：

1. **静态层（离线）：** AKEData 配方表 + 蓝图结构表。已有的 `皇帝产线-结构.json` 可以直接作为第一份结构数据：9 张蓝图、设备、准入口限速、溢流优先级。
2. **实况层（简报）：** 每种物品的库存、实际生产/消耗。
3. **设备层（俯瞰，按需）：** 可疑设备的状态和配方。

**推断流程（就是你教的分级生产规则）：**

1. 从最终产物往上游推。仓库 ≥ 约 89,900（上限 90,000）就算爆仓。
2. 产物爆仓：用它做原料的设备停下，上游消耗下降，都属正常，不报。
3. 产物没爆仓：再看它的原料。原料库存为 0 且消耗 ≥ 生产，才算真的缺。这时沿结构图往上追，直到第一个「供给受限」的点：准入口限速、矿点上限、管道上限、泵或水驱矿机。
4. 备路设备空闲（赤铜零件、优质饮料、蓝铁瓶液化息壤等），先查主路是否已爆仓，再下结论。
5. 简报里的收支本身也能反推配方去向。例：酸气产 6 = 沉积酸耗 6，同时液化重息壤和赤铜溶液都是 0，说明沉积酸只流向液气转化机。
6. 只有第 3 步追到某个设备、简报又看不出原因时，才进俯瞰点开设备确认。这样巡检量最小。

**你举的例子会这样推：** 赤铜块没爆仓、产量低 → 精炼炉不满速 → 赤铜矿库存为 0 且消耗 ≥ 生产 → 赤铜矿来自水驱矿机 → 清水不够 → 去俯瞰看对应的入水口或暗管：缓存是不是空的、管道是不是已到 120/分上限。

## 6. 准入口需要多少流体（推算，不用看）

对每个准入口 g：

```
需求(g) = Σ 下游设备 d 的 [ 配方每轮用量 × 60 / 每轮秒数 × 开工率(d) ]
```

- **下游设备：** 来自结构表的管道拓扑，即准入口后面接了哪些设备。蓝图预览或俯瞰确认一次后存进结构表，以后不用再看。
- **开工率：** 默认 1（满速）。产物爆仓时按第 5 节规则调低；如果读到了设备面板的「当前平均 x/分」，就用实测值。
- **供给类需求另算：** 固气转化机的「息壤气供给」、液气转化机的「液化息壤供给」、气体散布机的气体输入，最低都是 6/分，单独加上。
- **和上限比较：**
  - 需求 > 限速值：这个口卡住了下游，提示「放宽限速」，或者确认这是不是设计上故意限的（如起步口、最低供给 6）。
  - 需求 > 120/分：单根管道不够，提示加管。
  - 实际流量 < 需求，且下游缺料：上游供给不足，继续往上追。
- **分流器后的计算**沿用之前学到的规则：一路被限速为 L，另一路得到 S − L；设备产量 = 实际进料 ÷ 满速进料 × 满速产量。
- **配方时长要校准一次：** AKEData 表里的时长字段（`totalProgress` / `progressRound`）需要先拿游戏里几台设备的「平均 x/分」对一下换算关系。之前核对过的 2 秒、10 秒配方可以直接当基准。

## 7. 技术选型和分阶段路线

**建议的技术栈：** Python + MaaFw（PyPI 包 `MaaFw`）

- 识别逻辑写成 JSON 管线，复杂部分（行切分、纠错、诊断）用 Python 自定义识别。
- 诊断引擎也用 Python，直接复用已有的结构 JSON。
- 用 PyInstaller 打包成 .exe，清单里声明需要管理员权限。
- 界面先做最简单的，生成一份本地 HTML 报告；以后需要的话再换成 MXU 或 PySide6。
- 如果以后追求性能或想和 MaaEnd 统一，可以换成 Go/C++ 代理，管线 JSON 可以原样沿用。

**分阶段：**

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| P0 | 搭好 MaaFw 环境：连上游戏窗口、截图、识别出简报界面 | 能截到 1280×720 的简报截图并认出「简报」 |
| P1 | 简报读取器（V1–V5）：遍历每个地区、滚动读完所有行、导出 CSV/JSON | 和人工读的你的简报逐行一致，同名瓶子分得开 |
| P2 | 诊断引擎（第 5、6 节）：输入 P1 的结果，输出按优先级排序的问题清单 | 用你的简报得出和昨天手推一样的 11 步结论 |
| P3 | 俯瞰巡检（V6–V9）：只去 P2 指向的可疑设备，读状态和准入口 | 能自动定位并点开指定的准入口，读出限速 |
| P4 | 结构自动采集：从蓝图预览 + 俯瞰生成结构表，适配非皇帝产线的基地 | 换一个账号的基地也能出诊断 |

**P1 + P2 就已经比 QQ 机器人强**：数据由程序自己读，口径完全受控，覆盖全部地区。

## 8. 风险和待验证

- **账号风险：** 自动操作游戏可能违反用户协议。只读简报、少量点击，风险比 MaaEnd 的自动战斗、倒卖低，但不是零，发布时要写明。
- **必须管理员运行：** 已实测，不给就会被系统拦截输入。
- **分辨率：** 必须是 16:9；不同 DPI 缩放和全屏/窗口模式都要测。
- **游戏版本更新：** 界面布局或图标一变，模板就要更新。要把模板和 ROI 集中管理，并提供截图自检工具。
- **待验证 1：** 简报里同名行的顺序是否在不同账号间固定（如果固定，可以作为 V4 的备用方案）。
- **待验证 2：** 蓝图分享码能否离线解析出布局。MaaEnd 的「蓝图搬运工」只是把码输入游戏，没有解析；如果能解析，P4 的结构采集就可以不用视觉。
- **待验证 3：** 俯瞰里的设备状态角标有几种、各代表什么，需要整理一份对照表。
- **许可证：** 依赖 MaaFramework（LGPL）没问题；不要拷 MaaEnd（AGPL）的代码和素材，图标从 AKEData 原图自己做。
