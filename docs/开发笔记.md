《明日方舟：终末地》基建产线的诊断工具（Windows 本地程序）：读游戏简报判断产线哪里不对，还能自动巡检各分区的设备状态。

- **下载**：到 [Releases](https://github.com/Billtranscend/Endfield-Doctor/releases) 下载最新的灰度包，解压后看包里的「上手视频.mp4」和「使用说明.html」。

- **许可证**：源代码按 [AGPL-3.0](LICENSE) 发布；游戏素材、数据的版权归鹰角网络 / GRYPHLINE，不在授权范围内，详见 [NOTICE.md](NOTICE.md)。
- 本程序只读游戏画面、模拟键盘鼠标，不读写游戏内存、不改游戏文件。自动操作游戏可能违反游戏用户协议，风险自负。

调研见 `docs/调研-视觉诊断方案.md`。

## 开发环境

- Python 3.12，建 `.venv`，不入库：

  ```
  python -m venv .venv
  .venv\Scripts\python.exe -m pip install MaaFw opencv-python numpy
  ```

- 依赖：MaaFw 5.15.0、opencv-python、numpy
- OCR 模型：PaddleOCR PP-OCRv6 small，来自 MaaXYZ/MaaCommonAssets（MIT），放在 `resource/model/ocr`
- 游戏要求：画面（窗口客户区）16:9，偏离超过 1% 时 `game.connect` 拒绝连接，并按游戏所在屏幕给出改法（`game.recommend`）；任务运行中窗口尺寸变了就停（`GuardedController`）；显示器开着 HDR 时提醒（`game.hdr_on`）。见设计文档第十五轮。发送输入需要管理员权限
- 跨地区传输（可选）：档案 playbook.json 的 `transfers`，「蓝图」页可编辑；登记后终点地区这些物品「消耗大于产出」按正常处理

## P1：简报读取器

先在游戏里按 F10 打开简报，然后：

```
.venv\Scripts\python.exe src\brief_reader.py          # 读全部地区
.venv\Scripts\python.exe src\brief_reader.py 武陵     # 只读指定地区
```

结果保存为 `debug/brief_<时间>.json`：每个地区一张表，每行包含名称、灌装物（`fluid`）、库存、当前生产/消耗、理论生产/消耗、理论消耗是否标红。

做法：
- 整块 OCR 列表区域，按 x 坐标分列，按名称框的高度分行；名称只接受 AKEData 物品词表里的名字（`data/item_names_cn.json`）。
- 碰到列表上下边缘的半行跳过，等下一页完整出现时再读；库存为 0 时红色的「0」常被切成单独的框，所以把同一行拼起来读，读不到再单独裁剪重认。
- 翻页：每次 3 格滚轮（游戏把一次滚轮事件只算一格，所以逐格发送）。新页和已读结尾按行顺序对齐，只追加新行；不按名称去重，避免同名灌装瓶丢行。没有重叠时打印警告。
- 同名灌装瓶、耐压罐：用 AKEData 的液体/气体图标（`resource/icons/fluid`）带遮罩做彩色模板匹配；同时要求液滴内外颜色反差 ≥ 35、匹配差异 ≤ 420，否则判为空瓶（见 `src/fluid_icon.py`）。

2026-11-04 实测：武陵 169 行、四号谷地 98 行，翻页无漏行，与截图逐项核对一致；同名灌装瓶全部分对。

注意：
- 仓库上限按地区不同：武陵 90000，四号谷地 80000。判断爆仓时要按地区取阈值。
- 「当前」生产/消耗是实时值，两次读取之间会变；理论值也会随设备状态变化。

## P2：诊断引擎

```
.venv\Scripts\python.exe src\diagnose.py [debug\brief_xxx.json]   # 不给参数用最新一份简报
.venv\Scripts\python.exe src\brief_reader.py --diagnose            # 读简报 + 诊断一条龙
```

报告保存为 `debug/diagnosis_<时间>.md` 和 `.json`。按分级生产规则，从产物往上游推：

1. 产量低于理论的产物，先看能不能解释成正常：自己爆仓、下游爆仓回堵、备路未触发、蓝图设计限速。
2. 解释不了的沿原料往上追，停在第一个限制点：
   - 有大量库存的原料 → 原料有，这条线却没吃饱：**送不到或限速**（待确认，去俯瞰查进料口）；
   - 流体原料 → **流体供给不足**（待确认，查泵、暗管、准入口、管道 120/分上限）；
   - 产量低于理论的源头（矿、泵、采集）→ **来源不足**（待确认）；
   - 已按理论满产但不够分 → **设计内**。
3. 同一个根因影响到的产物合并成一条。持续耗库存的产物给出预计耗尽时间（提醒）。

要点：
- 库存为 0 不等于缺料：很多中间产物走传送带直送，不进仓库。
- 爆仓阈值按地区自动取（仓库上限 × 99.5%）。
- 互为逆向的配方（灌装 / 拆解、液气双向转化）只保留产物没有其他来源的方向。
- 「待确认」是简报推不出原因、需要进俯瞰看设备的地方，交给 P3。

配置（`data/`）：
- 蓝图档案 `data/blueprints/<名>/`（默认 `1.6皇帝产线`，命令行用 `--blueprint 名` 切换，由 `src/blueprint.py` 读取）：
  - `tier_rules.json`：备路触发条件（分级生产）和蓝图设计限速清单，可按用户的设计增删；
  - `reference_brief.json`：完全按蓝图搭好的基地的简报，用来对照源头物品（`src/sources.py`）。
  - `data/tier_rules.json` 仅作过渡保留，代码已不再读取。
- `recipes.json`、`item_id_names.json`、`item_names_cn.json`：由 `src/tools/build_data.py` 从 AKEData 生成。

2026-11-04 用新账号简报实测：武陵 5 条待确认、1 条设计内、3 条闲置；四号谷地 1 条待确认、1 条闲置。其余低于理论的都归到了爆仓、回堵或设计限速。

## P3：俯瞰巡检 + 联合结论 + 缺矿缺气液

先在游戏里 TAB 切到「工业」、站在协议区域内、CapsLock 进俯瞰，然后：

```
.venv\Scripts\python.exe src\patrol.py --sweep --area 应龙关        # 快速模式：扫遍整个基地，1–2 分钟
.venv\Scripts\python.exe src\patrol.py --sweep --deep --area 应龙关 # 深入模式：逐台点开读配方（慢，开发校验用）
.venv\Scripts\python.exe src\patrol.py --at "x,y,idle;x,y,blocked"  # 定点深查快速模式标出的坐标
.venv\Scripts\python.exe src\combine.py           # 巡检 + 简报 → 问题 / 待确认 / 正常 / 物流件信息
.venv\Scripts\python.exe src\sources.py           # 对照蓝图参考简报，报缺矿机 / 水口 / 气口（指明地区）
.venv\Scripts\python.exe src\diagnose.py --blueprint 1.6皇帝产线   # P2 报告前面加上 sources 一节
.venv\Scripts\python.exe src\full_patrol.py [--areas 武陵城,景玉谷,应龙关]   # 按分区依次传送、扫描、合并
```

速度（实际应用要兼顾准确和速度，开发时才逐台点开踩坑）：
- **快速模式**（默认）：连拍三张滤掉闪烁标记，用标记旁标签首字猜设备名（阻塞标记在设备顶部、标签在下方约 40 像素；空闲标记在产物图标左下、标签在上方约 45 像素），再从标记旁画着的产物图标认产物（空闲标记右上 14 像素、阻塞标记下方 78 像素处的圆形小图；灌装瓶按瓶身色相分赤铜/蓝铁/耐压罐、再认液滴；息壤/重息壤这类相近的两个都报）。不点任何东西。应龙关 42 台 62 秒、武陵城 45 台 174 秒。
- 满负荷产线上种植机、采种机的阻塞标记会持续两三秒，连拍滤不掉；合并时按「产物在正常流动（当前生产 ≥ 理论 × 0.85，或产多少用多少）」判为瞬时阻塞，不报问题。
- **深入模式**：逐个点开面板读名字、状态、配方；每个标记最多 7 次点击。应龙关整基地要几十分钟，只用于开发校验和 `--at` 定点深查（14 个点约 8 分钟）。
- 合并逻辑对快速模式的结果用「设备候选产物」兜底判断，待确认的坐标写进 JSON 的 `deep_check`，供定点深查。

巡检做法（`src/patrol.py`、`src/badges.py`、`src/panel_recipe.py`）：
- 俯瞰里找两种状态标记：红圆环斜杠 = 阻塞，蓝色 zz = 空闲中。物流件（取货口、存取线、暗管口）空闲时也有标记，归到「信息」一节：暗管出口空闲是「送不到」的直接线索。
- 深入模式点开设备读面板标题（设备名）、底部状态（生产中 / 阻塞 / 空闲中 / 未激活 / 运行中）、左侧仓库名（地区）、配方栏（原料 → 产物，含灌装瓶里的液体）。重叠处弹「选择目标」小菜单时自动选生产设备。
- 面板是否开着用右上角关闭按钮的模板判断；点到协议核心/次级核心弹出的全屏面板（含「跨地区传输」「设备制造」）只关不点；点击位置永远不落在底部建造栏和右侧菜单上。
- **坐标原点**：俯瞰可以一直平移到基地外，没有可靠的硬边界，所以不能「顶到角落」。做法：退出再进入俯瞰让镜头回到角色身上，缩到最远，这个画面（核心旁，有内容）作为原点；每个分区第一次扫描把它存成参考图（`resource/anchors/<分区>.png`），之后每次用相位相关补偿角色走位造成的偏移。再用能测位移的 `pan()` 向上、向左各 2.4 秒到扫描起点（撞到地图边界少走了也算得准；起点处是草地，不能在那里比对参考图）。这样不同次扫描的基地坐标能对上，定点深查（`--at`）才有意义。
- **平移与边界**：位移优先用相位相关估计。相关测不到时（草地没纹理、或真到了地图边界），看左上角小地图：镜头真的动了小地图平均像素差 20–27，顶在边界上只有 2–3；动了就按标定速度（593 像素/秒）算，没动就是边界。主画面的像素差均值/中位数、状态标记位置都试过，在草地上都分不出「移动」和「边界」。蛇形扫描一行里连续两屏没有设备标签和状态标记就换行，整行都没有就结束。
- 三种状态标记：阻塞（粉红圆环斜杠）、空闲中（蓝色 zz）、关闭（灰色圆圈叉，关掉的设备只有这一种标记）。

结果：`debug/patrol_<时间>.json`（`region` + `devices`）、`debug/combined_<时间>.md/.json`、`debug/sources_<时间>.md/.json`。

2026-11-04 端到端实测（完全按 1.6 蓝图搭的账号）：`full_patrol.py` 从应龙关出发，自动依次传送到景玉谷（29 台）、应龙关（42 台）、武陵城（31 台）并扫描合并，三处**问题 0**，待确认各 2–3 条（主要是没认出标签的标记，坐标已列入 `deep_check` 供定点深查），全程约 8 分钟。深入模式单独验证过武陵城 37 台（问题 0）。

跨分区：`src\navigate.py 武陵 应龙关` 自动走 M → 地区总览 → 分区 → 找基地图标（援建点 / 建设站）→ 传送 → 切工业模式 → 走进协议区域 → CapsLock 进俯瞰。景玉谷、应龙关实测一次到位。武陵城的协议核心在地图默认视野之外，`areas.json` 里配了特例：先把地图往下拖（滚轮对地图缩放无效）、用 `core_icon_main.png` 找、点开后在「协议核心 / 息壤中继器」重叠菜单里选协议核心、只有一个「传送」按钮。扫描前会先把镜头缩到最远（不同基地缩放不一样，模板和偏移都按最远缩放校准）。

只做武陵（武陵城、景玉谷、应龙关），四号谷地不管。已知限制：反应池 / 扩容反应池 / 废水处理机的面板布局不同，深入模式认不出配方（兜底按候选产物判断）。详见 `docs/P3-交接.md`。

## 调试工具

`src/tools/game_input.py`：截图 / 按键 / 按住 / 点击 / 按下-停顿-松开 / 滚轮 / 查看大写锁定。

- 发送输入需要管理员权限（游戏是管理员进程）。

  - 测试者在「蓝图」页导入作者的蓝图分析 zip 时，可以选「合并进现有档案」（`importer.import_zip(into=…)`）。

  - 物品图标只带用到的 177 个，并无损重压。
  - 不带 AKEData 原表。
  - 删掉 cv2 视频编解码、MaaFW 的 GPU 推理后端、Pillow 的 AVIF。
  - 结果：程序 zip 179 → 125 MB。
- 作者分析包「精简包」（`project.export(lite=True)`，界面导出时选，约 44 MB）只带导入后巡检要用的；完整包另带逐屏截图、原始帧和标注图，给开发核对。

### 蓝图档案：导入 / 新建 / 更新基准（界面「蓝图」页）

档案 = `data/blueprints/<名>/`：`areas.json`（地区→分区、主分区）、`playbook.json`（targets 最终产物目标）、`tier_rules.json`（备路规则，可为空）、`reference_brief.json`（基地正常时的简报 = 基准）。不用手改 JSON：

- **导入**：别人（蓝图作者）导出的档案 zip 或文件夹 → 「导入 zip / 导入文件夹」。`blueprint_tools.import_archive`。
- **新建**：「新建档案」向导（`Api.start_blueprint_survey`）：起名、选地区 → 程序读全部地区简报（存为基准）→ 每个在用地区打开地图总览逐分区找基地（`survey_region`，协议核心所在 = 主分区）→ 界面上勾分区、核对最终产物（`derive_targets`：产大于耗的固体产物；基准时爆仓/没在产的标灰待填）→ 保存（`save_archive`）。首墩这类蓝图里没用、别人可能用的基地也会被列出来。
- **更新基准**：基地改过、源头设备数量变了之后，趁正常时点一次（`start_update_reference`）。
- **导出 zip** 给群里其他人；**删除**。
- 没有备路规则的档案怎么判备路：`diagnose.Region.baseline_excuse` —— 产物在基准里就没跑满（备路/限速/轮换），现在不低于基准 × 0.9 就算正常；combine 的 `judge_idle` / `region_starved_hints` 同样用它顶替 tier_rules。1.6 档案回归 16/16 不变。
- 默认视野找不到基地的分区（基地在视野外、图标和设备重叠）向导会标出来，手动勾上后第一次巡检走自动探测；要稳定还是得在 areas.json 给该分区加 drag / icon / menu_pick（见 1.6 的武陵城）。

### 排查树与定向巡检

- `src/expert.py`：按基建维修群的人工顺序只用简报判（息壤 → 灼铜块 → 灼铜零件 → 重息壤 → 中容 → 其余目标），阈值从配方表（产出×60/秒）和基准理论算出台数，不手填。快速诊断和巡检报告首屏都是这棵树。
- ✗ 的步骤给出「去哪 / 看什么」，界面按钮「定向巡检这几处」→ `Api.start_targeted`：只去那些分区、只扫一遍、只点那类设备的面板（`Patrol.only_names` + `sweep_once`），每分区 3–6 分钟；全基地深入巡检保留给大改之后的体检。
